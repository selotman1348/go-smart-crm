# Decisions and open questions

This file records the decisions taken and the deviations from the docs, per iteration. Open questions are listed at the end, each with the assumption used until it is answered.

## Iteration 0 – Setup

| ID | Decision | Reason |
| --- | --- | --- |
| D-001 | Versions: Next.js 16.4 (App Router, React 19.3, Cache Components and Partial Prefetching on, as scaffolded), Tailwind CSS 4, shadcn/ui 4 (`base-nova` style, Base UI primitives), @supabase/supabase-js 2.119, @supabase/ssr 0.12, Supabase CLI 3.0 (dev dependency), zod 4, Vitest 5, Playwright 1.64, Node.js 24. | These were the latest stable versions at the start of the project. |
| D-002 | **Login uses the e-mail address and password** (Supabase Auth). UC-01 says "username": the e-mail address is the username. `User.username` from design.md 1.12 becomes a profile field in iteration 1. | Supabase Auth signs in with e-mail natively. Agreed with the product owner on 2026-11-05. |
| D-003 | **No self sign-up.** Sign-up is turned off in the Supabase project and in `supabase/config.toml`. Users are created by `npm run db:seed` or an admin through the Supabase dashboard. | Only internal users log in (requirements §2). |
| D-004 | Development uses a **hosted Supabase project**. The CI e2e job starts a **fresh local Supabase stack** on the runner, using the same CLI version as the dev dependency. | Docker is not used on the development machine. In CI, a fresh database each run proves the migrations apply from scratch, without any secrets. |
| D-005 | Supabase clients live in `src/lib/supabase/` and only `src/domain/` (and `src/proxy.ts`) may import them. An ESLint `no-restricted-imports` rule fails the lint when `src/app/**` or `src/components/**` imports `@supabase/*` or `@/lib/supabase/*`. | This enforces the repository rule in CLAUDE.md. |
| D-006 | The auth service (`src/domain/auth/auth-service.ts`) depends on a small `AuthClient` interface, not on the Supabase types. It is bound to the request's cookies in `src/domain/auth/index.ts`. | It can be unit tested with fakes, and the data platform can be replaced later. |
| D-007 | The session is checked twice: once in `src/proxy.ts` (optimistic redirect to `/login?next=…`), and again on the server in the app layout (`UserMenu`) and in every Server Action, through `src/domain/auth`. The `next` target only accepts same-site paths (`safeRedirectPath`). | The Next.js 16 guidance is not to rely on the proxy alone. The path check prevents open redirects. |
| D-008 | Sign-out ends only the current browser session (`scope: "local"`). | The Supabase default (`global`) would also sign the user out on their other devices. |
| D-009 | Sign-in errors show one generic message, "Invalid e-mail or password.", plus separate messages for rate limiting and unexpected failures. | The form does not reveal which e-mail addresses have an account. |
| D-010 | Seed users are fictitious, on the reserved `.example` domain: Alex Morgan and Sam Taylor (`@gosmart.example`). The password comes from `SEED_USER_PASSWORD`. | CLAUDE.md: fictitious seed data only. |
| D-011 | There are **no migrations in iteration 0**. `supabase/migrations/` is empty, and the schema, including the phase-2 hook tables, starts in iteration 1. | Iteration 0 has no tables of its own. |
| D-012 | `/` redirects to `/dashboard` (in `next.config.ts`). The app shell has only a header with the user's name and a "Sign out" button. Menu items are added when their pages exist. | No placeholder links before later iterations build the pages. |
| D-013 | **Deployment is prepared, not done.** The app builds for Vercel without configuration, and README.md has the steps. The product owner deploys, because it needs their Vercel and Supabase accounts. | Agreed on 2026-11-05. "Empty dashboard deployed" is complete once those steps have been run. |
| D-014 | CI uses GitHub Actions (`.github/workflows/ci.yml`) with two jobs: checks (lint, typecheck, unit tests, build) and e2e. It uses the pinned `supabase` dev dependency instead of the `supabase/setup-cli` action. | Local and CI then use the same CLI version. |
| D-015 | `createClient()` in `src/lib/supabase/server.ts` calls `connection()` before reading cookies. All server-side Supabase access therefore runs at request time, and is never part of a prerender or a runtime prefetch. It must not be called inside `"use cache"` functions. | Cache Components (D-001) rejected the session check during prerendering, because token validation reads the current time. A session is per request in any case. |
| D-016 | `npm audit` (2026-11-05) reports 2 low and 11 moderate findings, all in build tooling: `minimatch` and `deepmerge` through `eslint-config-next` / typescript-eslint and the `shadcn` CLI. The app imports only `shadcn/tailwind.css` from `shadcn`. They are accepted for now and should be re-checked when those packages update. | The only fixes npm offers are downgrades (`shadcn@1`, `eslint-config-next@15`). No finding is in code that serves requests. |

## Iteration 1 – Data model and master data

| ID | Decision | Reason |
| --- | --- | --- |
| D-017 | The schema is split into three migrations: `foundation` (helpers, enums, lookups, users), `crm_and_cases` (design.md 1.2–1.12) and `phase2_hooks` (design.md 1.13 and plan.md §3). Each file enables RLS on its own tables in the same transaction. | If a later file fails, no table is left without row-level security. |
| D-018 | **Naming deviations from design.md §1:**<br>• the table `"case"` keeps its name but must always be quoted in SQL<br>• User becomes `app_user`<br>• `from`/`to`/`cc`/`bcc` become `from_address`, `to_addresses`, `cc_addresses` and `bcc_addresses` (`text[]`)<br>• "enum + text" fields become a lookup FK plus a `*_text` column (`on_hold_reason` + `on_hold_reason_text`, `no_repair_reason` + `no_repair_reason_text`) | All of these except the enum fields are reserved words. An unquoted `user` silently means `current_user`, and an unquoted `case` fails loudly, so `case` can safely keep its name. |
| D-019 | Two fields come from the ER diagram, not the field tables: `document.communication_id` (COMMUNICATION–DOCUMENT) and `audit_log.case_id` (CASE–AUDIT_LOG). | The ER diagram shows these relationships. `audit_log.case_id` lets the History tab (UC-37) show changes to a case's child records too. |
| D-020 | Every table has `created_at`, `updated_at`, `created_by` and `updated_by`, maintained by the `set_audit_fields()` trigger. Signed-in users always get their own id and the current time. Only the service role may set `created_*` itself, so the seed can backdate history. | design.md §1: "every table". Users cannot fake who created a record. |
| D-021 | An `app_user` row is created by a trigger on `auth.users` for every new auth user (seed or dashboard), and existing users were backfilled. `username` is the e-mail address's local part, or the full address if that local part is taken. The trigger never blocks a sign-up. | Users created in the Supabase dashboard (Q-004) get a profile automatically. |
| D-022 | **RLS model:**<br>• `anon` has no access.<br>• Internal users (those with an `app_user` row, checked by `is_internal_user()`) have full CRUD on business tables.<br>• `status_history`, `audit_log` and `event` are select/insert only.<br>• Lookups and `app_user` are read-only.<br>• `api_client` (key hashes) is service-role only.<br>The model was verified live against the hosted project. | design.md §4: row-level security. Q-002 assumption: no rights per role yet. |
| D-023 | **Database constraints mirror the rules**, and the domain services check the same rules so users get readable messages:<br>• client code exactly when the account is a client, as `^[A-Z]{3,4}$` (BR-01)<br>• the case-number format<br>• VIN format and uniqueness<br>• `case_party.is_invoice_party` is a **generated** column (`role = owner_fleet_owner`, BR-02), with one owner/fleet owner per case<br>• quote-line sub-types must belong to their category, and deductions must be zero or negative<br>• mileage out at least mileage in<br>• discount and VAT percentages between 0 and 100 | Data stays valid even when it doesn't come through the UI (agents, scripts). |
| D-024 | Lookups are separate tables (`code` PK, `label`, `sort_order`, `active`). Their values live in the migration, because every environment needs them. The four unspecified lookups get proposed values (Q-005). The part catalog follows design.md 1.7, with wheel rims and tyres as separate items: 33 parts (Q-007). | Foreign keys keep the codes valid, and the lists are data, so they are easy to change. |
| D-025 | `completeness_rule` (plan.md §3 hook) has these columns:<br>• `client_account_id`: null means every client<br>• `stage`: intake, quote or invoicing<br>• `requirement`: a dotted key such as `case.vda_number`, which the completeness service (iteration 2/5) interprets<br>• `active`<br>Each combination of client, stage and requirement is unique. No rules are seeded yet. | design.md has no field list for this hook. A requirement key keeps the rules data-driven, without code in the database. |
| D-026 | "Reference data filled from manual quotes" (plan.md §3) is built as two views with `security_invoker` (RLS applies): `repairer_hourly_rate` and `quote_line_history`. The part catalog is the `part_catalog` lookup. | No duplicate data entry. The views fill up as quotes are entered. |
| D-027 | Each case has at most one quote per version (`unique (case_id, version)`). | design.md: "up to two Quote versions". Phase-2 AI proposals may need this revisited. |
| D-028 | **Hosted database workflow:**<br>• `scripts/supabase-remote.ts` runs the pinned CLI with `--remote=<ref>`, which it derives from `NEXT_PUBLIC_SUPABASE_URL`, and authenticates with `SUPABASE_ACCESS_TOKEN`.<br>• Scripts: `db:push`, `db:push:dry` and `db:types`.<br>• The generated `database.types.ts` is committed. CI regenerates the types from a fresh local stack built only from the migrations, and typechecks the app against them; any text differences are posted as a notice. | CLI 3.0 needs no database password or `link` for this. An exact text comparison failed on the first run: the hosted and local generators format some details differently, even though the schemas matched. |
| D-029 | **The seed is TypeScript** (`scripts/seed/`):<br>• pure data in `data.ts`, checked by unit tests<br>• deterministic UUID v5 ids<br>• insert-only (`ON CONFLICT DO NOTHING`), so a rerun never overwrites edits<br>• related data that matches each case's status (parties, damage, quotes, assessment, invoices, status history with events and audit rows)<br>• seeded events marked `delivered`, so a future webhook dispatcher doesn't replay history<br>E-mail templates, tasks, communications and documents are seeded in iterations 2, 4 and 5. | The seed must create Auth users through the admin API, and must work on the hosted project as well as in CI. |
| D-030 | **Fictitious Belgian-style seed data:**<br>• plates in the unissued `9-` series<br>• enterprise/VAT numbers with deliberately wrong check digits<br>• `000` subscriber phone numbers<br>• invented street names<br>• `.example` e-mail addresses<br>• VINs with a made-up prefix<br>Country is stored as `BE`. **DEM has no 2026 case**, so the demo's first e-mail case is DEM20260001. The repairer invoicing conditions use `invoices@gosmart.example`. | Agreed 2026-11-05. Seed data must be fictitious (CLAUDE.md), and plan.md §5 expects DEM20260001. |
| D-031 | **Accounts and Contacts UI:**<br>• native checkboxes and selects (shadcn `native-select`)<br>• client settings shown only for clients, repairer settings only for repairers; the service clears settings that don't apply<br>• Server Actions call `requireUser()` and then the domain service, and use `refresh()` after a save<br>• a contact requires an account (Q-006)<br>• search splits the input into terms that must all match, using escaped `ILIKE`; 25 rows per page | Native inputs post reliably with forms. Not trusting the client for authorisation follows the Next.js 16 guidance, and the escaping stops search input from changing the filter. |
| D-032 | The left navigation shows only the CRM section (Dashboard, Accounts, Contacts) for now (see D-012). | No placeholder links before later iterations build the pages. |

## Iteration 2 – Case management

| ID | Decision | Reason |
| --- | --- | --- |
| D-033 | **Audit trail by database trigger** (`audit_row_change`) on `case`, `case_party`, `damage`, `damaged_part`, `document`, `case_tag`, `vehicle`, `quote`, `quote_line`, `assessment` and `invoice`:<br>• inserts and deletes store the whole record as JSON; updates write one row per changed field<br>• the actor is the signed-in user, or the record's `created_by` for seed inserts, otherwise System; `app.actor_type=system` marks automatic changes (BR-03)<br>• vehicle changes are linked to a case's History through the vehicle id<br>• audit rows of a deleted case lose their `case_id`<br>Accounts and contacts are not audited. | UC-37 asks for "all changes on the case", including changes made outside the UI (agents, scripts). The History tab turns the rows into readable entries (`src/domain/history`). |
| D-034 | **Every status change goes through `change_case_status`**, a security-definer RPC. It checks `is_internal_user()`, rejects a status that has changed in the meantime (code PT409), and writes the status, `status_history` and the `status.changed` event in one transaction; the audit row comes from the trigger. Users no longer have write rights on `case.status`, `case_number` or `client_account_id` (column privileges). `create_case` (an invoker RPC, so RLS applies) writes the case, its owner/fleet-owner party, the first status-history entry and the `case.created` event atomically. | CLAUDE.md: every status change goes through the status engine and writes the history. The database enforces this, so no code path can skip it. The decisions themselves (which status, which number, which defaults) stay in `src/domain`. |
| D-035 | **Case numbering (BR-01):** the domain service takes the client's highest number for the current Brussels year and adds one (`nextCaseNumber`). If another user takes the same number at the same moment, the unique constraint rejects the insert and the service tries the next number, up to 5 times. An insert trigger also rejects any number that doesn't start with the client's client code. | The rule stays in the domain and is unit tested. The database guarantees uniqueness without a separate counter table. |
| D-036 | **App time zone is Europe/Brussels** (Belgian locale, D-030). It is used for the case-number year, "today", appointments (`datetime-local` input is converted to UTC, DST-safe) and the creation-date filter. Dates are shown as dd/mm/yyyy. | Belgian operations. A case created at 00:30 on 1 January gets the new year's number. |
| D-037 | **New-case defaults:** the creating user is case manager and assigned-to, the assignment date is today, and the client is added as owner/fleet owner (the invoice party, BR-02). Only the client is required (UC-16). | Agreed 2026-11-05. |
| D-038 | **Status engine** (`src/domain/cases/status-engine.ts`): any status can be set manually (design §2), the current status is rejected, and the only automatic target is "File follow-up – repairer (expert report OK)" (BR-03, iteration 3). The guard for BR-08 comes in iteration 5. | design.md §2. |
| D-039 | **Warning markers cover only BR-11 for now:** missing VDA/PO numbers for a client that requires them put a marker on the Case tab and show a note. They warn but don't block. The generic completeness engine (BR-13, `completeness_rule`) comes in iteration 5, together with BR-08. | Agreed 2026-11-05. UC-16 allows intake with minimal data, so blocking would get in the way (Q-013). |
| D-040 | **Documents** (UC-36):<br>• stored in a private Storage bucket `documents`: max 20 MB, PDF, images, Word, Excel, `.eml` and text<br>• paths `cases/<case>/<document>/<file>` or `shared/<document>/<file>`<br>• upload: the server checks the file and returns a signed upload URL, the browser PUTs the file straight to Storage, and the server registers it with the size and type Storage reports<br>• download: a route checks the session and redirects to a 60-second signed URL<br>• removal is allowed and is recorded in the History<br>The central `/documents` page holds shared documents (no case). | Direct upload avoids Vercel's 4.5 MB request limit for photos. Removal was agreed 2026-11-05. If the confirm step fails, a file can remain in Storage without a record; this is rare and harmless. |
| D-041 | **Parties** (UC-11):<br>• each role accepts certain account types: owner/fleet owner → client, intermediary → broker, insurer, expert, repairer, leasing company and third party → their own type<br>• driver and insured/tenant are people, recorded as a contact only<br>• a contact person must belong to the chosen account<br>• one owner/fleet owner per case (D-023)<br>• to change a party, remove it and add a new one | design.md 1.6: an account for organisations, a contact for people. |
| D-042 | **Vehicle tab** (UC-10): a case without a vehicle can find an existing one by plate or VIN (spaces and dashes ignored) and link it, or create a new one. A new vehicle's owner defaults to the case's client. A VIN that already exists gets a message pointing to the search. Editing the vehicle changes it for every case that uses it. | "One plate may return several cases" (UC-05): the same vehicle record is reused. |
| D-043 | **Case list:**<br>• built on the `case_overview` view; free-text search covers the case number, the plate (normalised: "9tka101" finds 9-TKA-101), the client and the references<br>• the status filter has an extra "Open (not closed)" option, which the client tiles (`open_cases_per_client`) use<br>• the repairer filter uses the case's first repairer party<br>• newest cases first, 25 per page | UC-04 to UC-06. |
| D-044 | The case screen tabs are separate routes: Case, Vehicle, Parties, Damage, Documents and History, each with Save and Close. Quote, Assessment and Communications are added in iterations 3 and 4. | Deep links, and each tab loads only its own data. |
| D-045 | **Implementation notes:**<br>• With Cache Components, Next keeps visited tabs mounted but hidden (React `<Activity>`), so e2e tests locate fields by role, which skips hidden elements.<br>• `NativeSelect` renders its children explicitly, and a `key` must come before a props spread.<br>• The upload widget is disabled until the page is interactive, and runs its Server Actions in a transition. | Found while testing. Without these, tests matched hidden duplicates, React warned about keys, and the widget could lose its state. |

## Open questions

| ID | Question | Assumption until answered |
| --- | --- | --- |
| Q-001 | Do users need "Forgot password" / password reset? It is not in the requirements. | No. An admin resets passwords in the Supabase dashboard. |
| Q-002 | Do case handlers and case managers have different permissions (for example, who may change a status or close a case)? This decides the row-level security policies in iteration 1. | All internal users have the same permissions (implemented in D-022). |
| Q-003 | How long should a session last, and should idle users be signed out? | Supabase defaults: a 1-hour access token, refreshed automatically while the browser is in use. |
| Q-004 | Who creates new internal users after go-live: an admin screen in the app, or the Supabase dashboard? | The Supabase dashboard. No user-management screen in version 1. |
| Q-005 | Please confirm the lookup values that iteration 1 proposed (see the foundation migration):<br>• **on-hold reasons:** awaiting documents / client / broker-insurer / parts, dispute, other<br>• **no-repair reasons:** cash settlement, below deductible, not covered, client declined, vehicle sold or returned, other<br>• **liability:** own fault, third party at fault, shared, unknown<br>• **circumstances:** collision with a vehicle / object, parking, vandalism, hail or storm, theft, glass breakage, animal, other | The proposed values are used. Changing them later needs only a data migration. |
| Q-006 | Can a contact exist without an account, such as a private driver, insured person or third party? | No. design.md's ER diagram gives every contact an account, so a private person goes under the client or a third-party account. Allowing it later is a one-line migration. |
| Q-007 | design.md 1.7 lists "wheel rims and tyres front/rear left/right". Are those separate parts (8 items) or one item per wheel (4 items)? | Separate rims and tyres: 33 parts in total. |
| Q-008 | design.md says a client code has 3–4 characters, but plan.md §2.1 matches case numbers on 2–4 capital letters. Which is right? | Client codes have 3–4 capital letters. E-mail matching (iteration 4) may still accept 2–4. |
| Q-009 | Is the vehicle category list complete? design.md says "e.g. electric, hybrid, diesel, petrol, light van". | Those five values, as an enum. |
| Q-010 | Must labour, other-cost and deduction lines always have a sub-type? | The database allows none. Iteration 3 (quote entry) decides the rule. |
| Q-011 | Should `app_user.email` follow e-mail changes made in Supabase Auth? | No. It is set when the user is created. |
| Q-012 | Should cases ever be deleted? This is not in the requirements. | No: there is no delete in version 1. A wrong case is closed instead. |
| Q-013 | Should missing VDA/PO numbers (BR-11) block anything, for example the repair order or invoicing, or only show a warning? | Warning only (D-039). Iteration 5 can make it blocking for invoicing. |
| Q-014 | Are the upload limits right: 20 MB per file; PDF, images, Word, Excel, `.eml` and text? | Yes. |
| Q-015 | Should a linked vehicle be replaceable on a case, for example when the wrong one was linked? | Not in version 1. The vehicle record can be edited, but there is no unlink. |
| Q-016 | Should the History tab also show changes to the accounts and contacts on the case? | No: only the case and its own records (D-033). |
